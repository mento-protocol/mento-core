Mento Engineering · Data Streams architecture

Mento V3 Oracles → Chainlink Data Streams

Moving the FPMM price path from a push model (an off-chain bot pays gas to relay Chainlink Data Feeds) to a keeperless pull model: signed Data Streams reports are verified on-chain, attached just-in-time to each swap. No keeper network — cost moves to swappers and is zero when a pair is idle. The deviation breaker is reworked so it no longer depends on a regular reporting cadence.

01 — As built today

Current push-based architecture

A Mento-operated bot calls relay() on a per-pair ChainlinkRelayerV1, reads latestRoundData() from up to 4 aggregators, composes to one rate, and writes to SortedOracles. Writing a report is what fires the breakers; the FPMM only ever reads.

02 — Proposed (revised)

Target keeperless pull architecture

DataStreamsRelayerV1 replaces the push relayer per pair. The only way a report gets written is when someone attaches a signed report to a transaction — normally a swap. There is no keeper box. relay() is permissionless, so anyone who wants the feed live (dapp, arbitrageur, integrator) can refresh it.

Keeperless design at a glance

  • No keeper. Reports happen only at swap time
  • Rate is fresh at execution — the swap brings its own report
  • Cost scales with usage, paid by swappers, $0 when idle
  • Recovery via permissionless relay() — incentive-driven
  • Deviation breaker is cadence-independent (§06)
03 — Code-grounded

The sequencing constraint (unchanged, now load-bearing)

Two facts from the live code define the swap-time order — and in a keeperless world this single ordering is what makes freshness, tripping and recovery all work without a heartbeat.

Fact 1 The relayer cannot call checkAndSetBreakers

BreakerBox.checkAndSetBreakers requires msg.sender == sortedOracles (BreakerBox.sol:321-325). Breakers fire as a side effect of SortedOracles.report() — so the relayer only calls report(), and BreakerBox needs zero changes.

Fact 2 The read path is view — verification must precede it

Verification runs as a state-changing pre-step earlier in the same swap tx; the existing view read then returns the freshly-written rate. Crucially the breaker is re-evaluated before the read.

04 — The core argument

Why removing the keeper is safe (and better)

The keeper had three jobs in quiet markets: keep the rate fresh, let breakers trip, let tripped breakers reset. The swap-time ordering in §03 covers all three — the keeper was largely redundant.

Freshness is intrinsic

The swap writes a fresh DON report before it reads, so _hasRecentRate always passes for the transaction that matters. A stale on-chain median in a quiet market is harmless — no value is moving.

Tripping is self-protecting

If the fresh report reveals a depeg, the breaker trips before the read — so the very swap that carried the bad price is rejected. You catch the depeg exactly when someone tries to trade on it, not in advance.

Recovery is incentive-driven

A swap attempt still runs report() + tryResetBreaker before the read. And relay() is permissionless — any arbitrageur or the dapp can refresh a stuck feed. Requires cooldown > 0 so reset is automatic, not manual.

The one residual

Pure view-only readers (UIs, other protocols) see a stale median in a quiet market and must trigger a relay() to refresh. This is inherent to any pull oracle — not a regression.

Cost model The keeper's cost curve was backwards for multi-chain

Keeper cost is fixed per pair, per chain — it multiplies with every new chain and is largest, relative to value, for the lowest-volume pairs. Keeperless flips it: cost is per-swap, paid by the swapper, and exactly $0 while a pair sits idle. Cost now tracks usage, not deployment surface.

06 — Breaker redesign

Slew-rate breaker (replaces the EMA)

A time-weighted EMA is not enough for a keeperless feed. It only makes the EMA accumulation frequency-invariant — but the trip test is still delta-since-last-report. With sparse, swap-driven sampling, a long quiet gap compares now against a price from hours ago, so legitimate slow drift trips falsely. An EMA assumes a regular cadence that a pull oracle does not have.

Insight Measure velocity, not absolute change

Every Data Streams report is fresh-from-the-DON. So a big move over a long gap is just the on-chain value catching up to reality (allow it); a big move over a short interval is a flash-crash / manipulation / glitch (trip it). A rate-of-change limit is not a workaround — it is more correct for pull.

The rule

# Δt = seconds between on-chain reports # (block.timestamp — objective, ungameable) relΔ = |cur − prev| / prev allowed = min(maxJump, baseJump + slew × Δt) trip if relΔ > allowed
  • baseJump — instantaneous tolerance (same-block jitter, rounding)
  • slew — how fast fair value may move (per asset class)
  • maxJump — hard ceiling regardless of Δt; a genuine discontinuity always trips

Cadence-independent: it never asks "how often did we sample," only "how fast did the price move." Pairs with ValueDeltaBreaker (fixed-band backstop) + MarketHoursBreaker (unchanged).

Worked example

FX-ish config: baseJump 0.5%, slew 2%/hr, maxJump 5%.

ScenarioΔtmoveallowedverdict
Quiet 3h, then jump10800s3%5%allow
Flash move30s3%0.52%trip
Old EMA on the 3h move—3%~1%false trip

The slew breaker allows the legitimate 3-hour catch-up but trips the 30-second flash — exactly inverting the EMA's failure mode under sparse sampling.

Config requirement Cooldowns must be > 0

With no keeper, automatic reset relies on tryResetBreaker firing on the next swap attempt or permissionless relay(). A cooldown of 0 forces manual governance reset — acceptable as a deliberate kill-switch, but it must be a conscious choice per feed, not a default.
